# 日志存储与可视化改造

## 已确认需求

- 操作记录、配置审计、收发信记录兼容 SQLite、MySQL、PostgreSQL，默认沿用当前业务数据库连接，不要求额外安装 MySQL，不自动迁移业务数据库。
- 设置导航在插件配置后增加日志入口，支持分类、时间筛选、分页与详情。
- 运行日志保存在 `log/运行日志`，按天写入；满七天的日文件压缩为独立的 `.log.gz`，启动补做，避免整周归档跨越清理边界。
- 压缩后的运行日志仍可在后台查看；仅在压缩校验通过后替换对应明文文件。
- 配置审计展示操作者、时间、具体字段及修改前后值；秘密只显示配置状态。
- 旧配置审计幂等迁移并保留原文件，不伪造历史缺失的变更详情。
- 用户于 2026-09-08 补充授权：三类日志均只保留最近 30×24 小时，启动补清理，运行期间定时滚动清理；压缩不重置保留时间。
- 数据库按记录时间分批删除；运行日志同时覆盖明文、压缩归档和边界日内的过期记录。查询也应用同一截止时间，不能展示等待下一次清理的过期记录。
- 清理仅作用于受管日志表和运行日志，绝不清理账号、邮件正文、附件、验证码业务表或其他项目数据库。15 GB 是容量预算而不是容量保证。
- 配置仍在原有五个 JSON 文件中，复用既有数据库配置，不新增 MySQL 专用日志连接。

## 验收边界

数据库连接沿用部署者当前配置，不能猜测或复用其他项目的密码。SQLite 实测通过不等于 MySQL、PostgreSQL 真实连接验收通过；方言检查与真实数据库测试必须分别报告。写入或清理失败必须可观察、可重试，不能无限排队或静默丢弃。

过期删除让数据库页可重用，但不保证数据库文件立即缩小；不在在线清理中执行全库 VACUUM、OPTIMIZE 或重建表，以免长时间锁住邮件业务。数据库保留期以记录创建时间为准，不因升级、迁移、压缩而延长。旧审计源文件仅用于迁移核对，不继续双写，暂不擅自删除。
