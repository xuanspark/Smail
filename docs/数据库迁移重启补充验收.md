## 重启响应缺陷与修复

重启接口交付信号后，主循环立即停止服务。原 HTTP／HTTPS 停服直接调用 `http.Server.Close()`，可能在响应及会话中间件完成前关闭连接。云端收到 `RemoteDisconnected`，同时服务日志确认重启请求已经被处理；不能把这种失败按偶发网络问题忽略。

新增统一停服方法：先调用 `Shutdown` 等待在途响应，期限为 10 秒；超时才强制关闭并保留错误。两种 Web 监听都使用此方法，没有使用任意等待或放宽客户端验收标准。

## SQLite 实机证据

最终实例：`/var/tmp/smail-review-runtime-20260921-051723/`。

本地归档：`test-log/production-remediation-20260921/migration-runtime-evidence/smail-review-runtime-20260921-051723/`。

1. 从空库初始化、写入配置历史，真实 SMTP 收信后由 IMAP／POP3 读取中文正文和附件。
2. 迁移预览后故意占用目标，执行返回 HTTP 409、`DATABASE_MIGRATION_TARGET_EXISTS`；记录为 `failed / TARGET_EXISTS`，目标内容未被覆盖。随后配置写入成功，证明维护锁已释放。
3. 成功迁移至 `migrated.db`，配置代次推进至 4；等待重启期间业务写入返回 HTTP 503、`DATABASE_RESTART_REQUIRED`。
4. API 内部重启返回 `accepted`，旧 Cookie 会话仍有效；PID 和 InvocationID 不变，这不是进程替换。
5. `systemctl restart` 后 PID 和 InvocationID 改变，文件描述符证实仅打开目标业务库，不打开源业务库。
6. 将本轮目标文件权限改为 `000` 后再次启动，进程退出码为 1、MainPID 为 0、状态为 failed；配置仍指向目标库，没有静默回退旧库。
7. 在收尾保障路径恢复目标权限为 `0600`，重新启动成功。内部重启、系统重启、故障恢复三阶段均验证登录、三种协议认证、旧邮件及新邮件正文和附件。
8. 新邮件仅写入目标库。源库完整逻辑摘要未变，源配置历史一条、目标一条，`kind/id/payload/digest` 完整一致。

进程证据：内部重启前后 `773001`，系统重启后 `773123`，故障恢复后 `773224`。

只有 `migrated.db` 是活动业务数据库；`smail.db` 和故意占用的 `occupied.db` 保留为离线证据，不是额外运行数据库，未经许可不删除。

保留两轮云端失败：`045727` 为验收器未先处理基础回归留下的待重启配置，被正确拒绝；`050341` 为真实重启响应中断，促成本次应用修复。失败记录均未删除或改成通过。
