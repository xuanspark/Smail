# 配置事务崩溃恢复补充验收

## 范围与结论

本项接续双 SQL 未提交复制中断验收，验证配置事务落盘、根配置切换与启动恢复。**本项不等于整个项目生产验收通过。**

- [✓] 真实终止测试子进程，而非仅在阶段钩子返回错误。
- [✓] 验证三种数据库配置选择下的回滚、保留新配置、重复启动与损坏拒绝启动。
- [✓] 修复新事务准备阶段崩溃残留导致下次启动被阻塞的问题。
- [✓] 云端重复终止测试、完整配置包回归与本地全量后端回归。
- [✓] 最新后端候选的隔离应用级 SQLite 迁移、邮件和重启回归。
- [ ] 完整应用的 SQL 提交与配置切换联合故障点、恢复过程再次被终止。
- [ ] 同一最终完整发行候选的统一生产验收与正式部署。

用户提供的管理员、域名和部署入口仍仅为测试参数，不转为产品验收标准。没有修改或暂存用户原来的 `云端全项目测试报告.md`，没有停止正式实例或其他项目。

## 修复的问题

旧实现先在 `data/transaction/<id>` 创建原始和候选目录，再写配置归档及首份事务清单。若在清单发布前突然退出，恢复扫描会遇到没有清单的活动目录，保留现场并拒绝启动。原配置虽然未变，但无法自动恢复可用。

新实现先写入 `data/transaction-staging/<id>`，完成归档、清单与目录同步后，再把整个目录原子重命名到活动事务区。发布之后才允许修改活动配置文件。

- 发布前突然退出：活动配置保持原样，残留暂存不参与启动恢复，也不阻塞下一次提交。
- 发布后发生错误：保留完整活动事务，由既有恢复算法决定回滚还是保留新配置。
- 暂存路径拒绝符号链接，避免配置归档写出预期目录。
- 旧版活动区中的无清单、损坏或不可信记录继续失败关闭，不自动删除或当作正常事务接受。
- 崩溃暂存保留为证据；这是文件归档目录，不是新增数据库。清理策略不在本次修复范围内。

没有向 HTTP、环境变量或正式运行配置增加故障注入开关。新增准备阶段钩子由测试直接设置，等待和强制终止逻辑均位于测试二进制。

## 故障矩阵与证据边界

每种 SQLite、MySQL、PostgreSQL 配置分别覆盖：

| 故障位置或状态 | 恢复结果 | 注入方式 |
| --- | --- | --- |
| 准备目录已创建、尚未写归档 | 保持旧配置，后续提交正常 | 正式提交路径钩子处终止子进程 |
| 归档与清单完整、尚未发布活动事务 | 保持旧配置，后续提交正常 | 正式提交路径钩子处终止子进程 |
| 已发布 prepared 清单 | 恢复旧配置 | 正式阶段钩子处终止子进程 |
| 仅一个分区被替换 | 恢复旧配置 | 使用正式原子替换函数构造落盘状态后终止 |
| 所有分区已替换、根配置未切换 | 恢复旧配置 | 正式阶段钩子处终止子进程 |
| 根配置已切换，清单仍是 sections_committed | 保留新配置 | 使用正式原子替换函数构造落盘状态后终止 |
| root_committed 清单已写入 | 保留新配置 | 正式阶段钩子处终止子进程 |
| verified 清单已写入 | 保留新配置 | 正式阶段钩子处终止子进程 |

另有两个强制终止后损坏归档的用例：分别改坏 original、candidate，启动必须拒绝，活动配置及损坏现场保留。独立测试保留旧版无清单活动目录的失败关闭行为，并验证暂存符号链接拒绝。

父进程确认到达目标点后强制终止子进程并等待退出；Linux 日志记录 `signal: killed`。随后两次调用正式 `NewConfigManager` 启动路径，检查代次、数据库选择、配置文件逐字节一致、锁释放及恢复幂等。

**上述三种数据库是配置选择矩阵，不是三种真实数据库的提交联合测试。** SQL 配置故意使用不可用的本地端口，证明文件恢复不依赖连接 SQL，也不会回退创建额外 SQLite。分区部分写入和根清单滞后是明确构造的磁盘状态，不声称在真实应用中捕获了对应指令间隙。再次成功启动不等于恢复途中再次被杀；进程强制终止不等于整机断电或物理存储耐久性验证。
