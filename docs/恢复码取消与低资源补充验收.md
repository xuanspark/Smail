## 超时定位证据

不降低 Argon2id 参数，不减少恢复码数量，不放宽探针 30 秒读取超时。密码算法仍为 `m=65536,t=3,p=1`，每轮生成十枚恢复码。

直接调用凭据服务的受限诊断使用新建 PostgreSQL 空库、专用账号、192 MiB 进程内存上限和 25% CPU 配额：

| 诊断实例后缀 | Go 内存目标 | 密码计算至事务开始 | 整体生成 | GC 次数 |
| --- | --- | --- | --- | --- |
| `20260921-082512` | 64 MiB | 23.753 秒 | 23.775 秒 | 138 |
| `20260921-082540` | 128 MiB | 24.079 秒 | 24.093 秒 | 10 |

这两个独立服务诊断没有显示明显的总耗时改善；数据库事务只占十几至二十几毫秒。不能仅凭 GC 次数差异宣称找到了完整应用的全部性能原因。前两次诊断启动遇到隔离挂载与执行路径错误，未进入应用测试，保留记录且专用账号已锁定。

| `20260921-083048` | 64 MiB | 30.208 秒 | 30.209 秒 | 客户端取消；尚未进入数据库事务，取消被服务识别 |
| `20260921-083337` | 128 MiB | 23.601 秒 | 23.619 秒 | 初始化及后续完整迁移通过 |

两个应用实例均保持 CPU 25%、进程硬上限 192 MiB、交换禁用、`GOMAXPROCS=1`、十枚恢复码和 30 秒读取超时，仅显式调整 Go 内存目标。直接证据确认失败发生在密码计算阶段，而非 PostgreSQL → SQLite 迁移执行阶段。内存目标变化与本次完整应用耗时改善存在对照证据，但不能从这一组样本外推所有负载下的性能。

原失败记录继续有效。128 MiB 是另一个明确标注的资源配置，不是把旧配置改写为通过，更不是生产容量或性能承诺。正式服务资源配置没有变动。

## 修改边界与反例

1. `GenerateRecoveryCodesContext` 接收 HTTP 请求上下文；旧无上下文入口保留，供兼容调用使用。
2. 每次 Argon2id 计算之间检查取消；单次计算本身不可中断，不改变哈希强度。
3. 凭据写入锁允许取消等待；取消不能释放其他请求持有的锁，也不能留下不可再用的锁。
4. 数据库事务使用请求上下文，插入和提交前检查取消；未提交事务统一回滚。
5. 自助及管理员代生成入口均传递请求上下文；管理员入口遇到密码计算繁忙时返回 `503`、`Retry-After: 1` 和 `AUTH_BUSY`。
6. 阶段日志只记录数量、耗时、阶段和成功／取消标志，不记录恢复码、哈希、口令或 Cookie。

反例覆盖：请求开始前取消、第一／第五／第十次计算后取消、等待凭据锁取消、等待数据库连接取消、第一／最后一次插入后取消、密码计算繁忙、互斥并发及非法解锁。成功路径继续检查十枚随机码及原 Argon2id 参数。

本修改保证已观察到取消且尚未提交的事务不会部分轮换恢复码。数据库提交已经成功后发生响应丢失，是另一种状态；不能承诺数据库提交与浏览器收到明文之间具有原子性。

## 工具与环境

- 隔离验收工具新增显式 Go 内存目标参数，默认仍是原 64 MiB；Go 目标与进程硬上限之间必须保留至少 64 MiB。
- 验收器读取进程环境时只保留 `GOMEMLIMIT`、`GOMAXPROCS`，不保存其他环境变量。
- 探针单独记录恢复码阶段和耗时，失败时不再把后续尚未创建的目标库误读为数据库损坏。
- 中间候选只重编译后端，复用未修改的前端与 Linux 插件资产，不能描述为全资产重建。
- 每轮使用新空隔离实例和新 SQL 库，不清空正式数据库，不停止正式 Smail 或其他项目，不删除离线证据。

中间候选 PostgreSQL → SQLite 实例 `20260921-083337`：内部 PID `794879` 不变，系统重启为 `795359`，故障恢复为 `795477`。三阶段源 PostgreSQL 连接数均为零，目标 SQLite 打开；运行目录只保留 `migrated.db`，没有第二个状态库。旧邮件、新邮件、正文和附件、配置历史原始字节、目标不可用时拒绝启动、恢复后读写均通过。
