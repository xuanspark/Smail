## 工具与权限控制

`test/tools/runtime_sql_migration.py` 通过正式迁移 API 完成切库。目标数据库不预创建；目标账号随机生成，只服务于本轮测试。连接凭据通过标准输入或子进程环境传递，不输出到证据或命令行。

- MySQL 仅对准确的目标库授权，下划线转义，不授予全局权限。
- PostgreSQL 为创建目标库临时授予 `CREATEDB`，迁移准备完成即撤销，结束后禁止登录。
- 只锁定本轮目标账号模拟故障，不停止共享数据库、不操作正式账号。
- 独立限时网络单元保持迁移前后的网络命名空间，避免把数据库桥接随应用进程替换丢失误判为应用缺陷。
- 全表行摘要证明源库不变，配置历史按完整行比较；MySQL 对字段取十六进制并保留空值，避免二进制字段破坏摘要序列化。

结果中的 `temporary_creation_privilege_revoked=true` 对 MySQL 是无操作的通用阶段标记；MySQL 从未获得 PostgreSQL 式全局临时建库权限，不能据此宣称撤销过这种权限。

## 扩大部署回归：保留失败及修正过程

本地 Windows 执行 `test/deployment/test_*.py` 时，86 项中有 2 个失败和 2 个错误：Linux `fcntl` 不可用以及平台路径分隔符差异。不能把它记录为全部通过，也未通过跳过测试消除问题。

| 云端隔离目录 | 结果与原因 |
| --- | --- |
| `smail-review-python-20260921-054448` | 105 项、8 个错误；证书测试要求隔离 root 身份及文件所有权 |
| `smail-review-python-20260921-054632` | 125 项、1 个错误；隔离 Nginx 工作进程 `setuid(65534)` 返回 `EPERM` |
| `smail-review-python-20260921-055549` | 125 项、零失败、零错误、零跳过，退出零 |

诊断目录为 `/var/tmp/smail-review-capabilities-20260921-055359/`。实际 `/proc/self/status` 显示能力边界为 `0xc1`，但许可及有效集仅为 `0x41`，缺少 `CAP_SETUID`；独立 Python 降权探针与隔离 Nginx 的系统调用跟踪均复现权限错误。这里确认的是实际进程缺少能力，不推断未经验证的系统组件内部原因。

仅增加 `AmbientCapabilities=CAP_SETUID` 后，有效集恢复为原边界内的 `0xc1`，小探针成功降权至 UID 65534，随后另建空工作目录重跑完整套件通过。能力边界仍仅为 `CAP_CHOWN CAP_SETUID CAP_SETGID`；保留私有网络、只读系统、隐藏正式目录及服务控制接口、禁止新增权限等隔离属性，没有使用完整 root 能力。

最终隔离单元内存限额 96 MiB、交换限额零、CPU 25%、进程数 32、运行时限 120 秒；实际运行约 7.6 秒，内存峰值 28.3 MiB，无交换使用。真实隔离 Nginx 换证重载与失败回滚用例通过，不能扩大为正式 Nginx 或全协议换证已经完成验收。

最终日志为 `python-linux-tests-20260921-055549.log`，SHA-256 为 `05e48d2669483bcfd921af5cfd46e6db1d90e012ed77ea294a4bcb8200a07581`，已与远端文件核对。摘要为 `python-linux-result-20260921-055549.json`。测试日志中的续期提示来自受控测试路径，不证明实际申请了公网证书。
