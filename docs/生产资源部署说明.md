## 候选默认预算

正式安装模板新增如下配置，部署人员需要先核算宿主机预算。默认值不是根据完整生产负载测得的安全容量。

| 配置 | 候选默认值 | 用途 |
| --- | --- | --- |
| `GOMEMLIMIT` | `256MiB` | 新建环境文件中的 Go 回收目标，不是进程硬上限 |
| `MemoryHigh` | `384M` | 控制组内存高水位 |
| `MemoryMax` | `512M` | 主服务及同组子进程的内存硬上限 |
| `MemorySwapMax` | `0` | 不以交换空间掩盖内存不足 |
| `CPUQuota` | `100%` | 默认最多使用一个 CPU 的时间配额，不是整机所有 CPU |
| `TasksMax` | `256` | 限制同组进程及线程数量，不等同于邮件用户数 |
| `OOMPolicy` / `KillMode` | `stop` / `control-group` | OOM 或停止时收尾整个服务进程组 |
| `Restart` / `RestartSec` | `on-failure` / `10s` | 故障后退避重启 |
| `StartLimitIntervalSec` / `StartLimitBurst` | `300s` / `3` | 五分钟内最多三次启动，防止持续重启占用主机资源 |
| `TimeoutStopSec` | `90s` | 覆盖队列 25 秒、数据库 35 秒及其他服务收尾时间 |

已有 `/etc/smail/smail.env` 始终保留，不自动添加或改写已有 `GOMEMLIMIT`。维护人员应在停服备份后人工检查该文件，保持 `root:root`、`0600` 权限。不要将整个环境文件输出到日志、聊天或验收文档。

若已有本机 systemd drop-in，它可能覆盖仓库模板。不能只看文件内容或 `daemon-reload` 成功；必须核对运行进程、服务管理器和内核控制组的实际值。

## 只读预检

工具只在 Linux 部署主机检查正在运行的 `smail.service`，要求 root、Python 3 和 cgroup v2。不会启动程序、改配置、重启服务、读写数据库或进行压测。

在服务器的本次审查源码目录运行：

```sh
python3 deploy/check_resources.py --reserve-mib 256
```

`256` 只是命令示例，必须按同机服务的增长及系统开销核算。工具要求显式指定且不得小于 `128`，不能为了通过检查降低已确定的预算。

预检逐项核对：

1. 服务处于运行状态，主 PID 位于本服务独立的统一控制组。
2. 内存高水位、硬上限、交换与任务数的 systemd 属性和实际内核值相符，CPU 配额有限。
3. 进程设置了有效的 `GOMEMLIMIT`，低于内存高水位，当前内存未达到高水位。
4. 从当前占用增长到 `MemoryMax` 后，主机仍有指定的保留内存；同时检查上级控制组的内存、任务数和 CPU 约束。
5. OOM 收尾、整个进程组停止、至少 90 秒且有界的停止期限、重启退避和启动频率限制有效，当前控制组没有累计 OOM 或 OOM kill。
6. 取证前后 PID、调用标识和所查服务属性一致，避免把重启前后的数据拼成通过证据。

工具仅从进程环境解析 `GOMEMLIMIT` 的数值，不输出其他环境项。报告中 `resource_checks_passed=true` 只表示这一次快照通过资源规则，`production_approved` 始终是 `false`；退出码 `0` 不构成完整生产放行。取证失败、权限不足、cgroup v1、属性缺失或检查不通过时返回非零。

主机资源随其他服务负载变化。瞬时检查没有为 Smail 预留物理内存，也不证明 MySQL、Scert 已分别受到合适的限制；必须另行确定这些服务的预算、监控并验证持续运行。

## 部署与远程验收

1. 恢复受信任 SSH 登录，核对主机身份、线上版本、服务 PID、重启计数、完整预算及 OOM 记录。不要复用已泄露的历史密码。
2. 先执行只读检查。旧服务缺少新规则时预期失败，保留结果作为整改前证据，不能通过重置计数掩盖 OOM。
3. 用最新源码构建产物；在 47 的独立目录和隔离网络创建清洁数据库验收实例，保持硬资源上限。正式 unit 的检查使用 `systemd-analyze verify`，不得仅用字符串断言代替系统解析。
4. 在受限的远程测试单元中执行 `python3 test/deployment/resource_policy_test.py`；也可使用统一部署测试入口 `node test/run.mjs deployment`。这些测试使用模拟快照和全新临时夹具，不访问业务数据库，不替代线上资源检查。
5. 完成正式安装流程、真实网页发信队列、中文附件、内部 `127.0.0.1:25`、混合认证和受控故障恢复，记录内存峰值、延迟、繁忙响应、任务数、OOM 和同机服务状态。仅用小样本成功不能声明最大容量。
6. 预算通过后安排停服窗口，备份双程序、unit、环境文件、所有数据库和密钥证书。安装程序不会自动停止正在运行的服务，部署时保留原数据与可回退产物。
7. 部署后重新执行只读预检与内部 SMTP 回归，检查限额、线上摘要和其他服务状态；未通过时停止放行，按备份方案恢复，不扩大预算以掩盖失败。

触发启动频率限制后，先保存故障证据并处理原因，再由维护人员决定恢复启动。不能在定时任务里循环 `reset-failed`，不能把自动重启当作队列和数据库的故障验收。
